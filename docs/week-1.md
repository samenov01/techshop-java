# Отчёт за первую неделю

Проект № 5: E-Commerce Platform with Order and Inventory Management.

## 1. Идея проекта

Я планирую сделать интернет-магазин компьютерных аксессуаров. В каталоге будут мыши, клавиатуры, наушники и другие небольшие товары. Покупатель сможет выбрать товар, добавить его в корзину и оформить заказ. Администратор будет следить за товарами, остатками и заказами.

На первой неделе я описал требования, продумал таблицы базы данных и подготовил макет интерфейса. Реализация приложения начнётся на второй неделе.

## 2. Пользователи

- Гость просматривает каталог, ищет товары и регистрируется.
- Покупатель (Customer) входит в аккаунт, собирает корзину, оформляет заказ и смотрит историю своих покупок.
- Администратор (Admin) управляет товарами и категориями, меняет остатки и статусы заказов, смотрит статистику продаж.

Гость — это посетитель без входа, отдельная роль в базе для него не нужна. При регистрации создаётся только Customer. Назначать себе роль Admin через форму регистрации нельзя.

## 3. Что должно работать в готовом проекте

1. Регистрация по имени, email и паролю, вход и выход из аккаунта.
2. Каталог с названием, описанием, ценой, категорией и доступным количеством каждого товара.
3. Поиск по названию, фильтр по категории и диапазону цен. Сортировка по названию и цене в обе стороны.
4. Добавление товара в корзину, изменение количества и удаление позиции.
5. Оформление заказа с именем получателя, телефоном и адресом доставки.
6. Расчёт суммы заказа на сервере и проверка остатка перед покупкой.
7. История заказов покупателя с составом, суммой и текущим статусом.
8. Добавление, просмотр, изменение и удаление товаров и категорий администратором с учётом связей в базе.
9. Обработка заказов администратором: подтверждение, отправка, завершение или отмена.
10. Статистика: количество заказов, сумма завершённых оплаченных заказов и продажи по датам на диаграмме.

Цены будут в тенге. Для первой версии доставка бесплатная. Подключать настоящую оплату не нужно: в проекте будет учебное подтверждение оплаты.

## 4. Основные правила

- Email должен быть уникальным. Пароль хранится только в виде хеша.
- Цена товара должна быть больше нуля, остаток — целым числом не меньше нуля. Количество в корзине и заказе — целым числом больше нуля.
- Повторное добавление одного товара увеличивает количество в существующей позиции корзины.
- Корзина не резервирует товар. Пока покупатель выбирает товары, остаток может измениться.
- При оформлении сервер заново проверяет цены и наличие. Сумма равна сумме произведений цены на количество по всем позициям. Значения с браузера не считаются окончательными.
- Если хотя бы одного товара не хватает, заказ не создаётся, остатки не меняются, корзина сохраняется. Покупатель получает понятное сообщение.
- Создание заказа, его позиций, списание остатков и очистка корзины должны выполняться одной транзакцией.
- Покупатель видит только свои заказы. Проверка прав выполняется на сервере.
- Состав и цены оформленного заказа не редактируются. Для отмены используется отдельная операция.
- Товар, который уже встречается в заказах, скрывается из каталога через `active`, чтобы сохранить историю. Категорию с товарами нельзя удалить, пока товары не перенесены в другую категорию.

Статусы заказа: NEW → CONFIRMED → SHIPPED → COMPLETED. Отменить можно NEW или CONFIRMED; после отправки отмена в этой версии недоступна. При отмене остатки возвращаются один раз. Повторная отмена ничего не списывает и не возвращает.

Статус оплаты хранится отдельно: UNPAID, PAID, REFUNDED. Учебная оплата переводит UNPAID в PAID у заказа NEW или CONFIRMED. Отправить можно только оплаченный заказ. При отмене оплаченного заказа ставится REFUNDED, при отмене неоплаченного остаётся UNPAID. Повторная оплата не должна менять уже оплаченный заказ.

## 5. Самая сложная часть

Нужно не допустить продажу сверх остатка, если два человека оформляют заказ одновременно. Например, на складе осталась одна мышь, и оба покупателя добавили её в корзину. Успешно оформить заказ должен только один из них.

Планирую при оформлении блокировать строки нужных товаров в базе до конца транзакции. Товары буду брать по возрастанию id, затем проверять остатки и уменьшать их. Второй заказ дождётся завершения первого и увидит обновлённый остаток. Это решение пока только запланировано; проверить его нужно при реализации.

## 6. Устройство проекта

Будут три основных слоя: Controller принимает HTTP-запросы, Service проверяет правила и выполняет операции, Repository обращается к базе через Spring Data JPA. Данные будут храниться в MySQL. На клиенте будут HTML, CSS и JavaScript, обмен с сервером — через Fetch API и JSON.

Для денег использую BigDecimal в Java и DECIMAL(12, 2) в MySQL. Проверки нужны и в форме, и на сервере. REST API будет использовать GET, POST, PUT и DELETE; успешные операции будут возвращать 200, 201 или 204, ошибки ввода — 400, отсутствие входа — 401, запрет доступа — 403, отсутствие записи — 404, конфликт остатка — 409.

В базе запланировано шесть связанных таблиц: users, categories, products, cart_items, orders и order_items. Подробное описание находится в database.md, схема — в папке design.

## 7. Макет интерфейса

Подготовлены четыре основных экрана:

1. Каталог: строка поиска, выбор категории, диапазон цен, сортировка и карточки товаров.
2. Корзина и оформление: список товаров, изменение количества, общая сумма и данные получателя.
3. Мои заказы: номер, дата, состав, сумма, статусы заказа и оплаты.
4. Панель администратора: список товаров, кнопки управления, заказы и статистика.

Формы входа и регистрации будут отдельными простыми страницами. Вход содержит email и пароль, регистрация дополнительно содержит имя. Ссылка на вход находится в шапке. На узком экране карточки будут идти в один столбец, а фильтры располагаться над ними.

Это черновой макет с вымышленными товарами и заказом. Подключения к серверу на первой неделе нет.
